Using ai-plugins the Right Way

A single, unified plugin suite under plugins/<name>/ built to run natively in both Antigravity 2.0 and Claude Code with model-agnostic core skills, isolated worktree swarms, and hook-enforced Spec Gates.

lean-runbook

Design + 5-Stage Build

Bundles lean-design (15–20m 3-doc suite) and lean-runbook (vertical-slice TDD loop with dual-protocol Spec Gate hooks).

swarmctl

Portable Local Swarm

MCP server + UNIX CLI giving Claude Code (and other harnesses) background workers, a shared board, share worktrees, and cross-vendor runners.

deep-review

3-Axis Code Review

Parallel isolated audits for correctness, structure, and testing, plus receiving-deep-review to triage findings.

build-loop

Full-Code Loop & Costs

Controller + model: inherit agents for full-code-in-plan loops, plus the standalone context-costs skill.

Need Use This Antigravity 2.0 Mechanism Claude Code Mechanism
Design or rearchitect a project before coding lean-design Native swarm + lean-design shim swarmctl (or Agent) + lean-design shim
Build a feature or multi-slice epic with Spec Gate lean-runbook Native swarm (workspace: "share") + root hooks.json swarmctl (share worktrees) + hooks/hooks.json
Parallel workers & cross-vendor review Native swarm / swarmctl Built-in swarm across Pools 1–3 (+ optional Pool 4) swarmctl MCP tools across claude, codex, gemini, opencode
Thorough branch / PR quality review deep-review 3 parallel read-only swarm workers (or subagents) 3 parallel deep-review:axis-reviewer Agent calls
Full-code-in-plan loop or token cost audit build-loop / context-costs Portable skill + references/version-custom-harness.md Native plugin + .loop/SEATS.md + Agent / codex / kiro

3. Installation Done Right

Every active plugin lives in plugins/<name>/ and is registered in .claude-plugin/marketplace.json. Running ./install.sh derives plugins, skills, and CLI shims dynamically, installs lean-runbook, lean-design, and swarmctl into ~/.local/bin, and auto-repairs legacy symlinks from old claude/ or antigravity/ layouts.

Antigravity 2.0

Links only plugins that ship a root plugin.json (currently lean-runbook) into ~/.gemini/config/plugins/, plus CLI shims into ~/.local/bin.

git clone https://github.com/effluvialsplurf/ai-plugins.git ~/Projects/ai-plugins
cd ~/Projects/ai-plugins

# Link Antigravity plugins + PATH shims (live edits)
./install.sh --antigravity

# Optional: also add portable review/cost skills
./install.sh --skills ~/.gemini/config/skills --only deep-review,context-costs,build-loop

# Check link health
./install.sh --antigravity --status
Do NOT install swarmctl as an Antigravity plugin — plugins/swarmctl/ intentionally omits root plugin.json so its MCP swarm tool never collides with Antigravity's built-in swarm tool. Also avoid installing lean-design/lean-runbook into ~/.gemini/config/skills if lean-runbook is already linked as a plugin.

Claude Code

Installs all 4 plugins (deep-review, build-loop, lean-runbook, swarmctl) with automatic hooks & MCP registration, plus CLI shims.

# Recommended (local clone — installs marketplace + PATH shims)
git clone https://github.com/effluvialsplurf/ai-plugins.git ~/Projects/ai-plugins
cd ~/Projects/ai-plugins
./install.sh --claude

# Or install directly from GitHub inside Claude Code:
/plugin marketplace add effluvialsplurf/ai-plugins
/plugin install lean-runbook@ai-plugins
/plugin install swarmctl@ai-plugins
/plugin install deep-review@ai-plugins
/plugin install build-loop@ai-plugins

# Test a single plugin live without installing:
claude --plugin-dir plugins/lean-runbook
Marketplace-only install (no install.sh)? No problem: lean-runbook's SessionStart hook injects the resolved absolute paths to runbook.py and design_check.py even before your first start, so skills work without ~/.local/bin shims. Restart Claude Code after installing plugins.

Installing on a machine that runs both harnesses? Just run ./install.sh (defaults to --all --link). Verify the repo itself anytime with ./tools/gate.sh (full) or ./tools/gate.sh --fast.

4. The 5 Abstract Roles & 4-Tier Dispatch Ladder

Core skills (lean-runbook, lean-design) never name provider model IDs or harness APIs. Every workflow maps onto five abstract roles and walks a deterministic 4-tier dispatch ladder:

Role Antigravity 2.0 Seat (harness-antigravity.md) Claude Code Seat (harness-claude.md)
orchestrator Normal main chat (keep thin; never /teamwork) Main Claude Code session (keep thin; read LOOP-STATE.md after compact)
explorer swarm scout on gemini-3.8-flash-low (Pool 1, inherit) Explore subagent on haiku (or read-only swarmctl worker)
planner swarm planner-<slug> on gemini-4-neon-medium (Pool 1, inherit) Fresh read-only Agent / build-loop:planner on opus
builder swarm builder-* / slice-* on claude-sonnet-5-5-medium (Pool 2), claude-sub (Pool 4), or gemini-4-argon-medium (Pool 3) in workspace: "share" swarmctl worker (runner=claude, workspace=share, sonnet) for parallel slices, or Agent (sonnet) for single slice
reviewer Strict opposite vendor: Claude built → gemini-4-neon-high; Gemini built → claude-opus-5-5-high or Pool 4 claude-sub (opus, high) Cross-vendor via swarmctl: runner=gemini or runner=codex (inherit, read-only). Same-family fallback: fresh opus + disclose in branch-review.md

5. Swarm Orchestration: Antigravity vs. Claude Code

Both environments share the exact same mental model — a shared message board, `@worker` mentions, read-only inherit workers, and isolated git worktree share workers — implemented natively in Antigravity and via the swarmctl MCP server in Claude Code.

Antigravity 2.0 Native swarm

NEVER use /teamwork with lean-runbook or lean-design. /teamwork spawns an internal orchestrator that lacks the swarm tool and forces every worker onto Gemini Models via invoke_subagent, burning one quota pool and defeating cross-vendor review.
  1. Start in a normal chat: Call swarm(action="models", all=True) to check live remaining quotas across Pools 1–3 (plus claude_status if Pool 4 claude-sub MCP is enabled).
  2. Load swarm_pane before adding the first workers so the Swarm Overview panel tracks threads cleanly.
  3. Pin exact models by role & pool:
    • Pool 1 (Gemini Flash / Neon): Scouts, Goldfish clarity/critic, Contract Planner, and Stage 5 cross-vendor review of Claude builds.
    • Pool 2 (Claude & GPT) / Pool 4 (claude-sub): Primary TDD builders and Stage 5 cross-vendor review of Gemini builds.
    • Pool 3 (Gemini 4 Argon): Concurrent Wave Slot B builder alongside a Claude builder.
  4. Use workspace: "share" for parallel builders (cap ≤3 concurrent, strictly disjoint files). Keep scouts, planners, and reviewers on workspace: "inherit" (read-only).
  5. Lifecycle rules:
    • waiting workers cost 0 tokens — keep scout alive across stages.
    • If a waiting worker's pool runs low (<25%), switch it via swarm(action="model", ...) instead of killing it.
    • Kill one-shot reviewers once consumed; kill share builders only after merging (killing deletes the worktree).
    • Critics inspect git diff epic/<slug>...slice/<slug> — never git checkout a branch already checked out in a worker's worktree.

Claude Code swarmctl MCP & CLI

When swarmctl@ai-plugins is installed, Claude Code gets four MCP tools mirroring Antigravity's board: swarm, post_message, read_board, and swarm_wait — plus full CLI parity via swarmctl.

  1. Discover available runners: Run swarm(action="models") (or swarmctl models). Default runner is claude (uses your local Claude subscription — no API key needed). Additional runners: codex, gemini, opencode, custom.
  2. Choose workspace mode intentionally:
    • inherit — worker runs read-only in your current checkout (scouts, planners, reviewers).
    • share — worker gets its own isolated git worktree under <repo>/.swarm/ and may edit, test, and commit.
    • unsafe — explicit opt-in only (writes directly to your main checkout).
  3. Standard coordinator loop:
    1. swarm(action="add", name="slice-a", workspace="share", runner="claude", brief="...")
    2. Continue coordinator work or spawn a second disjoint slice worker in parallel.
    3. post_message(text="@slice-a ...") to steer; swarm_wait(since=<seq>, timeout_sec=45) to block until replies arrive.
    4. Spawn a fresh cross-vendor reviewer (runner="gemini" or runner="codex", workspace="inherit") against git diff main...slice-a.
    5. Merge the branch, then swarm(action="kill", name="slice-a") (killing a dirty share worktree is blocked unless force=true).
  4. Agent tool vs. swarmctl: Use Claude Code's built-in Agent tool for quick, lightweight same-family subagents (Explore, deep-review:axis-reviewer). Use swarmctl for parallel isolated worktrees, long-lived board steering, and true cross-vendor reviews.

swarmctl Quick CLI Parity Reference

swarmctl models                                       # List available runners & default
swarmctl add slice-1 --workspace share --brief "..."  # Spawn isolated worktree worker
swarmctl add critic-1 --runner gemini --workspace inherit --brief "..."
swarmctl status                                       # Inspect live workers & worktrees
swarmctl post "@slice-1 run ./tools/gate.sh before finishing"
swarmctl wait --since 3 --timeout-sec 45              # Wait for board replies
swarmctl read --since 0                               # Read board history
swarmctl kill slice-1                                 # Retire & clean worktree (--force if dirty)

6. End-to-End Workflows

A. lean-design → lean-runbook (Primary Design & Build Flow)

For any non-trivial feature or architecture change, run lean-design first to produce a zero-duplication 3-doc suite (docs/designs/<slug>/{design,tech-plan,spec}.md, 15–20 min read budget, 100% BR-*/RISK-*/INV-*/SLICE-* traceability), then hand spec.md straight to lean-runbook:

STAGE 0
Scope Triage
Cheap explorer recon → Single Slice (≤3c / ≤600 LOC), Mini-Series (2–4), or Epic (>4).
STAGE 1
Compact Spec
docs/specs/<slug>.md (≤300L). Gate CLOSED
STAGE 2
Goldfish Gate
2 parallel fresh reviewers → user rulings → done goldfish. Gate OPENS
STAGE 3
Contract Plan
.loop/<slug>/plan.md (≤300L). Signatures, invariants & tests only — zero pasted code.
STAGE 4
TDD Build
builder commits on branch; 1-line quiet gate (tools/gate.sh) after every commit.
STAGE 5
Diff & Ship
Fresh opposite-vendor reviewer → branch-review.md → merge → finish.

lean-design CLI Commands

lean-design init <slug> --mode greenfield|redesign [--complex]
lean-design done brief <slug>
lean-design check docs/designs/<slug> [--strict]
lean-design done draft <slug>
lean-design done review <slug>
lean-design done resolve <slug>
lean-design status [<slug>]

lean-runbook CLI Commands

lean-runbook start <slug> [--epic <epic-slug>]
lean-runbook status [--all | --epic <epic-slug>]
lean-runbook done <spec|goldfish|plan|build|review>
lean-runbook skip gate --reason "<why>"
lean-runbook finish
lean-runbook pre-commit   # optional git hook check

B. deep-review + receiving-deep-review (Standalone Code Review)

Run /deep-review [axes] [fixed-point] [--comment] on any branch or PR. It pins the diff once and fans out up to three read-only reviewers in parallel — correctness, structure, and testing — writing a severity-ranked report to docs/reviews/. Follow up with receiving-deep-review to verify each finding before patching (never blindly accept a reviewer claim without checking the code).

C. build-loop + context-costs (Full-Code Plan Loop & Token Hygiene)

Prefer build-loop when you want complete code written into the plan before building. Initialize .loop/SEATS.md, .loop/PROJECT.md, and .loop/failure-classes.md once per repo; every agent in plugins/build-loop/agents/ uses model: inherit so seat choices in .loop/SEATS.md control all models without hardcoding. Read context-costs before running multi-agent sessions: cost scales with calls × context, so keep the coordinator thin, batch reads, use quiet 1-line test gates, and compact or start fresh between slices.

7. Spec Gates, Dual-Protocol Hooks & Out-of-Repo State

runbook.py implements a single pure decision engine (decide_write, decide_cmd, format_session_start) wired to both harnesses' native lifecycle hook protocols — plus a fail-closed pre-commit command for hookless environments.

Action Gate State Antigravity 2.0 (hooks.json) Claude Code (hooks/hooks.json)
Edit/write repo code file (incl. symlinks & cross-repo target) CLOSED decision: "deny" permissionDecision: "deny"
Write/edit/command touching state dir (~/.cache/lean-runbook) Any (even inactive) decision: "deny" permissionDecision: "deny"
Spec or plan exceeds 320 lines (write, edit_file, Edit, or Append) Active decision: "force_ask" permissionDecision: "ask"
Agent runs done goldfish, skip gate, start --force, or early finish Active / CLOSED decision: "force_ask" (user approves) permissionDecision: "ask" (user approves)
Session starts Active / Inactive Active: injectSteps summary + paths; Inactive: {} Active: additionalContext summary + paths; Inactive: 1-line script-path fallback

Why Parallel Worktree Gates Never Collide or Split-Brain

  • Unified state roots: LEAN_RUNBOOK_DATA (default ~/.cache/lean-runbook/repos/<sha256[:16]>/state.json) and LEAN_DESIGN_DATA (default ~/.cache/lean-design/repos/<sha256[:16]>/<slug>.json).
  • Zero split-brain: Neither CLAUDE_PLUGIN_DATA nor PLUGIN_DATA is used, because hooks and interactive Bash shells don't share those env vars. Both hooks and CLI shims always read the exact same state file.
  • Per-worktree isolation: The hash keys on each git worktree's resolved --show-toplevel path, so two parallel share workers automatically get independent Spec Gates while lean-runbook status --all (or --epic <slug>) aggregates all of them from your main checkout.

8. Common Pitfalls ("Do This, Not That")

Pitfall Why It Breaks Do This Instead
Running /teamwork in Antigravity Spawns an orchestrator without swarm; burns only Gemini quota and breaks cross-vendor review. Run lean-runbook / lean-design directly in a normal chat using native swarm.
Installing swarmctl as an Antigravity plugin Its MCP tool name swarm collides with Antigravity's native swarm tool. Let ./install.sh --antigravity skip swarmctl; use native swarm in Antigravity.
Installing lean-runbook in both plugins/ and skills/ Antigravity loads duplicate copies of lean-design and lean-runbook. Keep lean-runbook in ~/.gemini/config/plugins/ only; put only other skills in skills/.
Cramming >600 LOC or >3 commits into one slice Bloat triggers reviewer fatigue, slow fix loops, and muddy diffs. Split in Stage 0 into a 2–4 slice Mini-Series or an Epic with disjoint parallel waves.
Doing heavy file reads or diff reading in the Coordinator Inflates every subsequent turn's context cost across the entire session. Delegate scouting to explorer, planning to planner, and diff inspection to fresh reviewers.
git checkout slice/<slug> inside a read-only critic Fails with already used by worktree while a share worker still owns that branch. Inspect git diff <base>...slice/<slug> and git show slice/<slug>:<path> directly.
Letting the builder's own model family silently sign off Stage 5 Shared blind spots miss spec drift and edge-case bugs. Assign opposite vendor (Antigravity swarm or Claude swarmctl); if single-vendor, disclose in branch-review.md and run full boundary/mutation tests.
Committing .loop/ scratch state to git Pollutes feature PRs with ephemeral loop ledgers and review scratchpads. Keep .loop/ untracked (or in .git/info/exclude); commit only code, tests, and approved docs.
